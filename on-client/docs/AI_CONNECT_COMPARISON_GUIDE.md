# 워크벤치는 되는데 AI 연결만 안 될 때 — 비교추론 안내

「계정 연결 확인(워크벤치·native 로그인)」은 성공하는데 「AI 연결」(AI 앱 승인)이
`ALEKOV_CONNECT_OUTCOME_UNKNOWN` 등으로 확인 불가·실패하는 상황을 좁히는 방법입니다.
핵심은 **성공한 쪽이 이미 증명한 것을 먼저 빼고, 갈라지는 다리만 본다**는 것입니다.

이 문서는 안내용입니다. 제공 파일(`public/`·`src/`·`tools/`)은 바꾸지 않고,
비밀값·열쇠·설정 파일 내용은 어디에도 적지 않습니다.

## 1. 두 경로는 어디가 같은가

| | 계정 연결 확인(워크벤치) | AI 연결(AI 앱 승인) |
|---|---|---|
| 화면 버튼 | 「계정 연결 시작」「로그인 확인 완료」「현재 로그인 확인」 | 「AI 연결 시작」「승인 페이지 열기」「승인했으며 연결 확인」「상태 다시 확인」 |
| 상대 | 포털(Workbench 승인 화면) + native 호스트 | **CLCO 게이트웨이** + 포털 승인 + 자격 저장소 |
| 서버 경로 | `/api/native-login/*` | `/api/alekov-connect/*` (내부적으로 게이트 `…/api/apps/aleph-on/connect/start·redeem`) |
| 오류 코드 | `NATIVE_HOST_*`, `NATIVE_LOGIN_*` | `ALEKOV_CONNECT_*` |
| 저장 | 로그인 연결 상태 | AI 자격(credential) — 별도 저장소 확인 절차 |

같은 포털 승인 방식을 공유하지만, AI 연결은 게이트 통신과 자격 저장 확인이라는 **별도 다리**가 더 있습니다.

## 2. 비교추론 — 대조군이 지운 후보

워크벤치 연결 성공이 이미 증명한 것(=원인 후보에서 제외):

- 앱 서버가 켜져 있다 — 안 켜져 있으면 native 쪽도 `NATIVE_LOGIN_NETWORK`/`CLIENT_TIMEOUT` 이었을 것
- `-NativeHostConfig` 설정이 읽혔다 — 없으면 `NATIVE_HOST_DISABLED`/`NOT_MOUNTED`
- 포털 승인 페이지·확인 번호 절차가 동작한다
- 현재 계정·프로젝트·세션 scope 조회가 된다 — 이게 안 되면 양쪽 다 `CONTEXT_UNVERIFIED`

그러므로 의심 범위는 **AI 연결에만 있는 다리**로 좁아집니다:

1. CLCO 게이트웨이까지의 통신 (연결·TLS·5xx)
2. 게이트의 `connect/start`·`connect/redeem` 응답이 계약에 맞는가 (상대 AI 쪽 구현 포함)
3. 자격을 받은 뒤 **자격 저장소(vault) 저장 확인** — 워크벤치 경로는 이 다리를 쓰지 않으므로 native 성공으로 증명되지 않은 부분
4. 운영자 측 앱 권한 발급 상태

## 3. 오류가 뜬 자리로 층을 가른다

| 어느 시점에 떴는가 | 실패 지점 | `OUTCOME_UNKNOWN` 의 뜻 |
|---|---|---|
| 「AI 연결 시작」 직후 error | 게이트 `connect/start` 호출 | fetch 예외(전송 중 끊김), 게이트 5xx·408·425·429, 또는 시작 응답이 ok인데 필드가 어긋남 |
| 「승인했으며 연결 확인」 후 unknown, 또는 「상태 다시 확인」에서 확인됨 | redeem 폴링 → 자격 수령 → 저장 확인 중 어느 곳 | redeem 응답 5xx·전송 실패, 저장 확인 끝을 못 봄, 알려진 코드가 아닌 예외 |
| (참고) `RESPONSE_INVALID` | 게이트가 "대답"했으나 계약과 다름 | 상대 측 응답 형식 문제 — 전송 실패와 구분됨 |
| (참고) `STORAGE_UNVERIFIED` | 자격은 왔는데 저장 확인 불일치 | 게이트는 응답했음 — 이 PC 자격 저장소 쪽 의심 |

코드 근거: `src/ai/connection.mjs`(fetch 실패·5xx·catch-all → `OUTCOME_UNKNOWN`),
`src/connection/manager.mjs`(finish 정산: 알려진 코드가 아니거나 자격 저장 확인 실패 → `unknown`).

`OUTCOME_UNKNOWN`은 **"서버가 받았는지조차 확정 못 함"**이라는 뜻입니다.
포털·게이트 쪽에서는 승인·발급이 됐을 수 있습니다. 그래서 자동 재시도를 하지 않는 것이고,
"실패"로도 "성공"으로도 적지 않습니다.

## 4. 학생이 순서대로 할 일

1. **「연결 도움정보 보기」를 먼저** 누릅니다. `phase`·`reason`·`component`·`version`·`observedAt`·`routes` 등 안전한 값만 나옵니다. 내용을 직접 읽은 뒤 「확인했으며 복사합니다」로 복사해 둡니다.
2. **어느 버튼에서 떴는지**를 적습니다(「AI 연결 시작」인지, 「승인했으며 연결 확인」·「상태 다시 확인」인지) — 위 §3 표의 행을 정해 줍니다.
3. 포털 승인 페이지가 실제로 열렸는지, 확인 번호를 입력해 승인까지 했는지 적습니다.
4. 「상태 다시 확인」을 **한 번** 눌러 서버가 아는 현재 상태를 봅니다(재시도가 아니라 조회입니다).
5. 계정 연결 확인이 `connected` 인지, 같은 PC·같은 계정으로 진행 중인지 확인합니다.
6. 그래도 안 되면 **멈추고 도움정보를 담당자에게** 보냅니다. 게이트 로그·포털 요청 상태·자격 저장소 확인은 담당자 몫입니다.

하지 말 것: 같은 버튼 연타(자동 재시도 없음), 작업 폴더 삭제·재생성, 열쇠·설정 내용 붙여넣기, 확인 불가를 "됐다"로 적기.

## 5. 담당자 쪽에서 확인할 것

- 게이트 서버 로그: 해당 시각·요청의 5xx 여부
- 포털에서 그 승인 요청(deviceId)의 상태 — 승인됐는데 앱이 못 받은 것인지
- 자격 저장소에 credential 이 실제 들어갔는지(`persisted`)
- 상대 AI 쪽 구현이 `start`·`redeem` 응답 계약(`alekov.app-connect.*.v1` 스키마, 확인 번호 형식, 승인 주소)을 지키는지

## 6. AI 에이전트에게 보내는 지시문 — 작성법

이 문제를 AI 에이전트에게 맡길 때 지시문에 들어갈 것과 뺄 것입니다.

**반드시 넣을 것**

- 오류 코드 원문 그대로: `ALEKOV_CONNECT_OUTCOME_UNKNOWN` (의역·번역 금지)
- 대조군 한 줄: "같은 앱에서 계정 연결 확인(워크벤치)은 성공한다" — 이 한 줄이 탐색 범위를 절반으로 줄입니다
- 실패 지점: 어느 버튼·어느 단계에서 떴는지
- 「연결 도움정보 보기」의 JSON 원문(안전한 값만 있음)
- 근거를 스스로 찾게 할 파일 위치: `docs/CONNECTION_TROUBLESHOOT.md` §5 "AI 앱 승인" 표, `src/ai/connection.mjs`, `src/connection/manager.mjs`, `public/ai-connect.mjs` 의 `CONNECT_MESSAGES`

**반드시 적을 경계**

- 제공 파일을 고치지 말 것 — 학생이 손대는 곳은 `student/extension.mjs` 뿐
- 비밀값·열쇠·토큰·설정 파일 내용을 읽거나 출력·저장하지 말 것
- "확인 불가"를 성공이나 빈 결과로 처리하지 말 것
- 자동 재시도·폴링 추가 같은 코드 변경 제안을 하지 말 것(이 흐름은 사람이 직접 누르는 방식이 규칙)

**요구할 산출물**

1. 이 코드가 나오는 코드상 분기 목록(파일·줄 근거 포함)
2. 각 분기를 "학생이 확인 가능" / "담당자 확인 필요" 로 분류
3. 지금 눌러도 안전한 다음 동작 하나(보통 「상태 다시 확인」 또는 도움정보 수집)

### 복사해서 쓸 수 있는 지시문 예시

```text
내 앱에서 AI 연결(AI 앱 승인)이 ALEKOV_CONNECT_OUTCOME_UNKNOWN 으로 끝납니다.
같은 앱에서 계정 연결 확인(워크벤치/native 로그인)은 성공합니다.
실패는 「<AI 연결 시작 / 승인했으며 연결 확인 / 상태 다시 확인>」 단계에서 확인됐습니다.

연결 도움정보(비밀값 없음):
<연결 도움정보 보기로 복사한 JSON 붙여넣기>

on-client 저장소에서 다음을 하세요:
1. docs/CONNECTION_TROUBLESHOOT.md §5, src/ai/connection.mjs,
   src/connection/manager.mjs, public/ai-connect.mjs 를 읽고
   이 코드가 나오는 모든 분기를 파일·줄 근거와 함께 열거하세요.
2. 각 분기를 "학생 PC에서 확인 가능" / "담당자(게이트·포털·저장소) 확인 필요"로 나누세요.
3. 지금 눌러도 안전한 다음 동작 하나만 제안하세요.

제약: 제공 파일(public/, src/, tools/)을 수정하지 않습니다. 비밀값·설정 파일 내용을
읽거나 출력하지 않습니다. 확인 불가를 성공으로 표시하지 않습니다. 코드를 고치지 말고
분석만 하세요.
```

## 7. 다른 학생의 AI 쪽으로 연결하는 경우 주의

상대편(게이트·포털 뒤의 AI 구현)이 다른 학생의 작업물이면, `RESPONSE_INVALID` 계열은
**상대 측 응답이 계약과 다르다**는 뜻일 수 있고, `OUTCOME_UNKNOWN` 은 내 요청이 상대 측에서
5xx 로 죽었을 수 있습니다. 어느 쪽이든 내 화면에서 확인할 수 있는 범위는 도움정보까지이며,
게이트·포털·저장소 확인은 담당자가 합니다. 내 작업 폴더를 지우거나 바꾸는 것으로
해결되는 문제가 아닙니다.
