# 3~6차 방어전 안내: 내 보안 운영 웹앱을 만듭니다

3차에는 기존 6~12단계와 XDR 필수 과제를 마무리합니다. 4차부터는 그동안 만든 자료실과 판정 코드를 바탕으로, 실제로 운영할 수 있는 보안 운영 웹앱을 직접 개발합니다. 마지막에는 공격을 받고, 무너진 곳을 고치고, 다시 막히는 것을 증명한 v1.0을 냅니다.

이 과정에서 돈을 낼 일은 없습니다. 유료 가입, 카드 등록, 개인 AI API 키 충전, 유료 호스팅, 도메인·장비 구매를 요구하지 않습니다. 유료 도구 사용이나 결제로 추가 점수를 주지 않습니다.

## 2. 4차에 만드는 것

시작 틀은 `student-kit/defense-product-v6` 입니다. 로그인 확인, 저장소, 주소 연결, 공개 시험은 들어 있습니다. 여러분은 `src/product/index.mjs` 의 함수를 채웁니다. 함수마다 지켜야 할 약속이 주석에 적혀 있습니다.

| 날짜 | 목표 | 그날 끝났다고 볼 기준 |
|---|---|---|
| 10/19(월) | 시작 틀 연결, D1 정책 | 정책을 바꾸면 다음 요청부터 판정이 실제로 달라집니다. |
| 10/20(화) | D2 사건, D1 다시 확인 | 같은 사건이 두 번 와도 한 번만 저장하고, 순서가 뒤섞여 와도 시각 순으로 찾아봅니다. |
| 10/21(수) | D3 대응, 앞 기능과 연결 | 승인하기 전에는 아무것도 막지 않고, 승인한 뒤에는 대상만 막힙니다. |

### D1 정책

정책은 규칙 목록입니다. 규칙마다 허용(allow), 거부(deny), 추가 확인(step_up) 가운데 하나를 정합니다. 규칙이 하나도 맞지 않으면 거부합니다. 관리 작업자(operator)만 정책을 바꿀 수 있고, 일반 사용자가 바꾸려 하면 거부해야 합니다. 정책을 바꿀 때마다 판 번호가 하나씩 올라가고, 예전 판으로 되돌려도 새 판 번호로 기록합니다. 두 사람이 동시에 정책을 바꾸면 한 사람만 성공해야 합니다.

### D2 사건

사건은 "누가 언제 무엇을 했는가"를 적은 기록입니다. 같은 사건이 두 번 들어오면 한 번만 저장하고, 같은 번호인데 내용이 다르면 저장하지 않고 충돌로 알립니다. 형식이 틀린 사건이 하나라도 섞여 있으면 그 묶음 전체를 받지 않습니다. 짧은 시간에 읽기가 몰린 사용자는 사건 묶음(incident)으로 만들어 대응할 수 있게 합니다.

### D3 대응

사건 묶음을 보고 차단을 제안하고, 관리 작업자가 승인하면 그때 집행합니다. 같은 요청이 두 번 와도 한 번만 집행해야 합니다. 집행이 잠시 실패하면 정해진 간격(1초, 2초)으로 두 번까지 다시 시도하고, 그래도 안 되면 "보류"로 남깁니다. 보류를 성공으로 표시하면 안 됩니다. 응답이 사라졌을 때는 이미 집행됐을 수 있으니, 다시 보내기 전에 상태부터 확인합니다.

### D4 복구

정책과 사건을 정해진 형식으로 백업하고, 복원할 때는 먼저 전체를 검사합니다. 내용이 바뀌었거나 다른 프로젝트의 백업이거나 비밀번호·토큰·감사 기록 같은 것이 들어 있으면 거부합니다. 거부할 때는 아무것도 바꾸지 않아야 합니다. 감사 기록은 어떤 경우에도 지우지 않습니다.

## 3. 5차에 하는 것

- **총공세:** 심판이 정상 요청과 공격 요청을 섞어 새 값, 새 순서로 보냅니다. 정상 사용자는 계속 쓸 수 있어야 하고, 공격은 막혀야 합니다.
- **변경 요구:** 미리 알려 준 세 가지 유형 가운데 하나가 나옵니다(`CHANGE_REQUESTS.md`). 코드를 크게 갈아엎지 않고 반영한 뒤, 앞 기능이 깨지지 않았는지 다시 시험합니다.
- **배포본 묶기:** 설치 안내(README), 구성 설명, 정책 목록, 시연 방법을 정리하고 v0.9 태그를 붙입니다. 다른 사람이 안내만 보고 같은 결과를 낼 수 있어야 합니다. 이 문서들은 4차 동안 기능을 만들면서 조금씩 써 두세요. 이틀 안에 처음부터 쓰기는 어렵습니다.

## 4. 6차에 하는 것

총공세에서 뚫렸거나, 정상 사용자를 잘못 막았던 요청을 모두 찾아 원인을 적고 고칩니다. 고친 곳마다 같은 공격을 다시 넣는 시험을 추가합니다. 그다음 정해진 장애 상황(`RECOVERY_SCENARIOS.md`)에서 정상 상태로 되돌리고 v1.0 태그를 붙입니다.

6차는 "다 막았다"가 아니라 "뚫린 곳을 찾고, 고치고, 다시 막히는 것을 증명했다"로 판정합니다. 총공세에서 덜 막았더라도 수복으로 만회할 수 있습니다.

## 5. 어디에서 돌리나

- **기본:** 3차까지 쓰던 자기 무료 Vercel·Supabase 프로젝트를 그대로 씁니다. 자기 프로젝트의 서버 SQL 실행 환경에서 키트의 `supabase/product_kv.sql` → `supabase/product_operator.sql` 순서로 초기화합니다. operator 템플릿에는 이메일 확인이 끝난 본인 계정 UUID와 서버의 `PRODUCT_PROJECT_ID`와 같은 프로젝트 ID를 넣습니다. 중앙 ALEPH DB에서 실행하지 마세요. 서비스 키는 서버 환경변수에만 둡니다.
- **대체:** 서버를 실행하기 전에 `node scripts/test-identities.mjs --local`로 연습 계정 A·B·OP를 만들고 `npm run start:local`로 내 PC에서 돌립니다. 계정 재생성·삭제는 서버를 중지한 뒤 진행하고 서버를 다시 시작합니다. 판정 기준은 같습니다. 자세한 내용은 [FREE_PATH.md](./FREE_PATH.md)를 보세요.
- 공식 시험 신원 등록인 `node scripts/test-identities.mjs --supabase --register`는 현재 구현 미완료입니다. 등록 URL을 설정해도 계정을 생성하지 않고 종료 코드 2로 끝납니다. 먼저 로컬 연습을 진행하세요. 이 안내가 운영 심판·집행 제공자·중앙 DB 연결 완료를 보증하지는 않습니다.

## 6. 어떻게 판정하나

- 공개 시험은 22개이며 미구현 업무 기능을 검사하는 시험은 처음에 실패하는 것이 정상입니다. `npm test`로 확인하세요. 공개 시험을 통과한 것만으로는 끝이 아닙니다. 공식 판정은 시험 환경이 준비된 뒤 같은 약속에 새 값과 새 순서를 넣어 확인합니다.
- 화면에 "성공"이 떴는지가 아니라, 실제 요청의 결과와 저장된 기록으로 판정합니다.
- 아래 가운데 하나라도 확인되면 점수가 높아도 "제품 완료"로 보지 않습니다.
  - 로그인하지 않았거나 권한이 없는 사람이 자료를 읽거나 바꿀 수 있음
  - 승인하기 전에 차단이 집행됨
  - 복원하다가 자료가 사라짐
  - 정상 사용자가 모두 막힘
- 우리 쪽 시험 환경이 준비되지 않아 확인하지 못한 항목은 "미검증"으로 따로 표시합니다. 여러분의 실패로 세지 않습니다.
- AI 도구를 써서 빨리 만들어도 괜찮습니다. 다만 새 입력으로 실제로 돌려 보고, 무엇을 왜 고쳤는지 설명할 수 있어야 합니다. 쓴 토큰 양이나 코드 줄 수로는 점수를 주지 않습니다.
